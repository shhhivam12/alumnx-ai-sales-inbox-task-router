# Sales Inbox Agent Dataset

This directory is an isolated, deterministic dataset package for the Alumnx AI Labs Sales Inbox Agent challenge. It does not depend on or modify the project in the parent directory.

See [`HACKATHON_PLAN.md`](HACKATHON_PLAN.md) for the full product, architecture, implementation, evaluation, deployment, and submission plan.

## Quick Start

```bash
python scripts/generate_dataset.py
python scripts/validate_dataset.py
```

Both scripts use only the Python standard library. Generation is deterministic with seed `20260808`.

## Files

| File | Purpose |
| --- | --- |
| `data/inbox.json` | The 250 valid email messages supplied to the application |
| `data/team_roster.json` | The challenge's exact six-person routing roster |
| `data/batches/batch_001.json` | Initial messages 1-100 |
| `data/batches/batch_002.json` | Initial messages 101-200 |
| `data/batches/batch_003.json` | Fifty replies on existing actionable threads |
| `data/ground_truth/expected_decisions.json` | Per-message create, update, skip, or no-op labels |
| `data/ground_truth/expected_tasks.json` | Final task state after replaying all decisions |
| `data/eval/eval_60.json` | Stratified 60-message review worksheet with draft labels |
| `data/fixtures/invalid_ingest_cases.json` | Invalid API inputs, isolated from production data |
| `data/manifest.json` | Counts, seed, generated file list, and SHA256 checksums |

`inbox.json` is the application input. Never send ground-truth, evaluation, manifest, or invalid-fixture files to the routing model.

## Corpus Shape

The corpus contains 200 initial threads and 50 replies.

| Initial scenario | Count |
| --- | ---: |
| Enterprise RFP, RFI, tender, or large inbound deal | 34 |
| SMB enquiry | 30 |
| Marketing | 26 |
| Alliances | 22 |
| Finance | 26 |
| Genuine ambiguity requiring triage | 18 |
| Out-of-office | 12 |
| Newsletter | 10 |
| Unsolicited vendor spam | 16 |
| Automated bounce | 6 |

Expected message operations are:

| Operation | Count | Meaning |
| --- | ---: | --- |
| `create` | 156 | First actionable message in a thread creates one task |
| `update` | 42 | A reply changes the existing task; it must use PATCH |
| `skip` | 49 | Policy-excluded message; no task mutation |
| `noop` | 3 | Actionable-thread acknowledgement with no new task facts |

Seven replies deliberately change the original owner. Ten threads receive more than one update. Five actionable threads receive an out-of-office reply that must not alter the existing task.

## Edge Coverage

The valid corpus includes:

- Government and PSU tenders below the INR 10 lakh threshold
- INR 9,99,999, exactly INR 10,00,000, and INR 10,00,001 boundary cases
- `lakh`, `lac`, `L`, `crore`, `cr`, comma-grouped, decimal, and Hinglish amounts
- Invoice, payment, pipeline, and sponsorship amounts with different semantic roles
- Deadlines at 71 and 73 hours, relative dates, event-date decoys, and superseded reply dates
- English, Hinglish, HTML fragments, attachments, quoted chains, typo-like filenames, and personal senders
- Vendor spam containing marketing, PR, webinar, integration, and sales language
- Explicit negations such as "not a reseller request" and "not a customer purchase"
- Multiple asks owned by different teams and value ranges crossing the ownership threshold
- Missing companies, conflicting intent, prompt-injection text, and unconfirmed government context
- Replies that revise budget, deadline, company, scope, owner, or category
- A GST-refund zero-count trap: GST appears in the corpus, but no email is classified as a GST refund

Invalid schema tests are intentionally kept in `data/fixtures/` and are not included in `inbox.json` or any production batch.

## Ground Truth

Each decision records:

- `operation`: `create`, `update`, `skip`, or `noop`
- `expected_task`: complete task payload for a create
- `expected_patch`: minimal mutable field changes for an update
- `task_key`: stable local key used to replay a thread before the shared API assigns a task ID
- `rationale` and `evidence`: human-readable decision support
- `confidence_range`: acceptable calibration band, not a required exact model score
- `facets`: structured metadata useful for grounded analytics

`source_email_id` remains the first actionable email after updates. The final task file is generated by replaying every decision in inbox order and is checked byte-for-byte by the validator.

## Evaluation Warning

`data/eval/eval_60.json` is a prepared review worksheet, not proof of hand labelling. Its `review_status` intentionally remains `draft_requires_manual_review`.

Before reporting metrics in `EVALS.md`:

1. Review each email without looking at its draft label.
2. Record your own expected decision and fields.
3. Resolve disagreements and document difficult cases.
4. Change the review status only after completing that work.
5. Report real measurements, including failures you did not fix.

Synthetic labels must not be described as independently hand-labelled evaluation results.

## Assumptions

- Formal RFPs, RFIs, and tenders route to Aarti regardless of value.
- Government and PSU tenders also route to Aarti regardless of value.
- A direct inbound deal exactly at INR 10 lakh routes to Rohit; only values above it route to Aarti.
- Multi-owner requests create one triage task instead of multiple tasks.
- Date-only actionable deadlines are treated as local end-of-day.
- Meeting preferences and event dates are not task deadlines unless a response or submission is explicitly required.
- Invoice and payment amounts are not deal values.
- Sponsorship package values are retained as deal values, matching the challenge's worked example.
- A non-actionable reply on an existing thread leaves that task unchanged.

## Validation

The validator checks schema and types, exact enums, unique IDs, timezone-aware timestamps, contiguous thread indexes, one-to-one labels, lifecycle replay, immutable task provenance, final task equality, batch composition, evaluation integrity, invalid fixture isolation, edge coverage, manifest counts, and SHA256 checksums.

Successful output begins with:

```text
Dataset valid: 250 messages / 200 threads / 156 tasks
```
