# Interview Preparation — Sales Inbox Task Router

Use this as a speaking guide, not a script to memorize word-for-word. The strongest
interview answer is: state the business risk, explain the decision, name the tradeoff,
and point to how it was tested.

## 1. The opening answer

### 30-second version

> I built a hybrid AI routing system for a noisy B2B sales inbox. Gemini converts
> messy English, Hinglish, HTML and reply chains into typed evidence, but deterministic
> Python owns the actual routing rules, thresholds, dates, confidence, suppression and
> task writes. The system persists one task per thread in Supabase, records skipped
> emails and every update for auditability, and exposes a grounded chat whose numbers
> are computed from stored data rather than generated by an LLM.

### 90-second version

> The business problem was not merely classifying emails. It was ensuring that valuable
> work becomes the correct task, junk does not create work, replies update the existing
> thread task, and an operations user can verify what happened. I separated probabilistic
> language understanding from deterministic business decisions. Gemini extracts a strict
> Pydantic schema: intent, direction, amounts with roles, deadlines with roles, company
> evidence and explicit reply changes. Python then applies documented precedence, such as
> government tenders always going to Enterprise Sales and deadlines within 72 hours being
> high priority. Supabase stores raw emails, immutable decisions, current thread state,
> task events, skipped reasons, feedback and chat audits. Ingestion is idempotent by email
> identity and serialized per thread, so replaying a batch cannot create duplicate tasks.
> The frontend previews raw data before routing, shows live decisions and evidence, and
> unlocks batch-scoped grounded chat after routing completes.

## 2. The core design principle

The most important sentence in the interview is:

> Gemini extracts; deterministic code decides.

Why:

- LLMs are useful for messy language, Hinglish, intent direction, forwarded content and
  semi-structured dates or amounts.
- LLMs are not trusted with exact enums, ₹10 lakh arithmetic, 72-hour comparisons,
  idempotency, database writes or owner precedence.
- Typed extraction reduces the LLM to an evidence-producing component.
- Deterministic policy makes every important decision reproducible and unit-testable.
- If Gemini fails, a conservative deterministic extractor keeps processing visible and
  lowers confidence rather than silently dropping an email.

Why not a pure keyword classifier:

- Vendor spam deliberately contains words such as “PR,” “webinar” and “content marketing.”
- Direction matters: “we sell SEO services to you” is spam, while “we want to sponsor your
  newsletter” is a legitimate Marketing request.
- Replies contain quoted historical budgets and dates that must not be re-applied.
- Real messages contain typos, HTML and Hinglish such as `1.2 cr` and `20th ko`.

Why not let Gemini route directly:

- Model output can change between calls.
- It may invent missing values or ignore rule precedence.
- Exact owner/category enums and numeric boundaries are grader-scored.
- A prompt instruction inside an email must not be able to force assignment.

## 3. Architecture to draw on a whiteboard

```text
React/Vite on Vercel
  ├─ JSON paste/upload and raw preview
  ├─ sequential chunks of at most 100
  ├─ live decision polling and evidence UI
  └─ completed-batch grounded chat
                    │ HTTPS, exact CORS origin
                    ▼
FastAPI on Render
  ├─ grader Task API: /tasks and /users
  ├─ app API: /ingest, /api/tasks, /api/stats, /api/chat
  ├─ normalization + suppression
  ├─ Gemini structured extraction
  ├─ deterministic routing/confidence
  └─ reconciliation/idempotency
                    │ TLS PostgreSQL connection
                    ▼
Supabase Postgres
  ├─ grader-visible tasks
  ├─ raw emails and immutable decisions
  ├─ delivery attempts and ingest runs
  ├─ one current row per thread
  ├─ task event history
  ├─ feedback
  └─ chat audit
```

Why FastAPI:

- Pydantic gives strict request/response validation and exact enum contracts.
- The routing layer is already Python, so no cross-language policy duplication.
- Automatic OpenAPI helps verify the public grading contract.

Why Supabase Postgres:

- The challenge requires persistence across restarts.
- Unique constraints and row locks are better guarantees than application-only checks.
- Relational filters and aggregates make chat answers immediate and exact.
- JSONB preserves rich evidence without weakening the normalized operational tables.

Why no browser-to-Supabase or browser-to-Gemini calls:

- API keys and database credentials must remain server-side.
- The backend must validate identity, scope and allowlisted operations.
- It creates one auditable path for every number and side effect.

## 4. End-to-end ingestion lifecycle

Explain one batch in this order:

1. `POST /ingest` validates the locked candidate ID and 1–100 typed emails.
2. A run row is created with a request hash and optional client batch ID.
3. Emails are grouped by `thread_id` and sorted by `message_index`, receive time and ID.
4. Processing happens in waves with at most one email per thread per wave. This permits
   small Gemini batches while preventing a reply from overtaking its predecessor.
5. Each email is normalized; current reply content is separated from quoted history.
6. Existing identity/content hashes are checked before model work.
7. Deterministic suppression handles obvious OOO, bounces, newsletters, vendor spam and
   empty acknowledgements without spending a Gemini request.
8. Remaining messages are sent to Gemini in structured batches of at most five.
9. Deterministic policy corrects or supplements explicit INR amounts and deadlines, then
   decides owner, category, priority, due date, value and confidence.
10. The reconciler locks the thread, rechecks idempotency, creates or patches the one task,
    and records the decision/event/current snapshot.
11. `/ingest` returns only after every item has a confirmed stored outcome.

Why synchronous ingestion:

- It is required by the problem statement.
- A `200` must mean the task writes are complete, not merely queued.
- It simplifies the grader’s read-after-write behavior.

Why processing waves:

- A large batch may contain multiple replies from the same thread.
- Parallelizing those replies could apply message 2 before message 1.
- One message per thread per wave preserves causal order while still batching unrelated
  threads for Gemini efficiency.

## 5. Suppression logic

Suppression is intentionally conservative because spurious tasks are heavily penalized.

### Out of office

Requires both OOO-style subject and body signals. Legitimate buying or collaboration
language prevents suppression.

### Automated bounce

Requires a mailer-daemon/postmaster sender plus delivery-failure language.

### Newsletter

Requires broadcast language plus an opt-out signal such as unsubscribe or manage
preferences. A request to sponsor or advertise in a newsletter is protected.

### Vendor spam

Requires a selling-to-us phrase plus a sales call-to-action. Buyer/collaboration signals
protect legitimate inbound demand.

### Acknowledgement

A reply containing only “thanks,” “received” or “noted” produces no task change.

Interview phrasing:

> I did not treat triage as a dumping ground for junk. Triage is for actionable ambiguity;
> suppression is for messages that create no work.

## 6. Routing precedence

The current owner decision order is:

| Precedence | Evidence | Result | Reason |
|---:|---|---|---|
| 1 | Material asks for different owner groups | Triage | Choosing one owner would drop another ask. |
| 2 | Government/PSU tender | Aarti / enterprise | Explicit business override. |
| 3 | Formal RFP, RFI or tender | Aarti / enterprise | Formal procurement belongs to Enterprise Sales. |
| 4 | Invoice, PO, payment, GST, vendor billing | Divya / finance | Finance intent overrides money-as-sales confusion. |
| 5 | Sponsorship, webinar, content, PR/media | Meera / marketing | Money in sponsorship is not a sales deal. |
| 6 | Reseller, channel, integration, OEM, referral | Karan / alliances | Partnership value is not direct deal value. |
| 7 | Direct purchase/demo/product enquiry | Sales by value/evidence | Apply the ₹10 lakh boundary. |
| 8 | Other actionable ambiguity | Triage | Honest uncertainty is safer than a false assignment. |

Direct-sales boundary:

- Above ₹10,00,000 → Aarti.
- Exactly ₹10,00,000 or below → Rohit.
- Demo/product enquiry with no stated value → Rohit.
- Unresolved direct purchase with no usable value → triage.
- A range crossing the threshold, such as ₹8–15 lakh, becomes `null` and triage.

Multi-ask nuance:

- Invoice + GST is not triage because both asks belong to Divya.
- Reseller + technical integration is not triage because both belong to Karan.
- Product purchase + webinar is triage because Sales and Marketing are different owners.

## 7. Human review and confidence

Human review is rule-driven, not caused by an arbitrary confidence threshold.

Triage is selected when:

- Material asks belong to different teams.
- No clean supported intent exists.
- A value range crosses the sales threshold.
- Commercial scope is intentionally unavailable.
- A public-sector opportunity is not yet an official tender.
- The sender has not aligned between multiple materially different approaches.

After triage is selected, its confidence is deliberately constrained to `0.30–0.54`.
The chat/UI therefore uses `≤ 0.54` as the low-confidence reporting boundary. Low
confidence does not independently re-route a normal decision to triage.

Confidence starting points:

| Situation | Base |
|---|---:|
| Different-owner triage | 0.42 |
| Other triage | 0.45 |
| Confirmed suppression | 0.96 |
| Hard deterministic rule | 0.92 |
| Explicit deal budget | 0.88 |
| Rohit/SMB route | 0.80 |
| Other supported route | 0.84 |

Adjustments:

- Two or more amount/deadline/organization evidence elements: `+0.03`.
- Extracted owner candidate agrees with deterministic policy: `+0.02`.
- Truncated content: `−0.08`.
- Domain-inferred company support exists as `−0.08`, though the current route does not
  activate domain inference.
- Multi-material assignment outside triage: `−0.18`.
- Degraded extraction: subtract `0.20`, cap hard rules at `0.65`, other results at `0.30`.
- Global clamp: `0.05–0.98`; triage clamp: `0.30–0.54`; round to three decimals.

Why this is not a probability:

> It is an explainable operational confidence score used for review prioritization. I
> would not call it statistically calibrated until blind human labels and reliability
> curves have been completed.

## 8. Priority and deadline decisions

High priority:

- An actionable submission, confirmation, payment or media-response deadline is at or
  within exactly 72 hours of `received_at`.
- The request is overdue.
- Explicit urgent intent is combined with immediately/today/tomorrow language.

Low priority:

- Explicit statements such as no rush, nothing urgent, only exploring, routine request
  or invitation only.

Medium priority:

- The default when neither high nor low evidence exists.

Important distinction:

- Meeting preferences, event dates and OOO return dates are not actionable task deadlines.
- “Sometime next week” remains `due_date = null` unless it is actually phrased as a
  required response/submission deadline.
- `tomorrow EOD` is resolved from the email’s timestamp/timezone, not the server clock.
- Exactly 72 hours is high because the rule says “within 72 hours” and the implementation
  intentionally treats the boundary inclusively.

## 9. Amount and company policy

Only `deal_budget` and `sponsorship_package` roles can populate `deal_value_inr`.

The following do not become deal value:

- invoice amount;
- payment amount;
- pipeline estimate;
- revenue-share/downstream figure;
- unrelated number.

Only explicit INR amounts are used. Foreign currencies are not silently converted because
there is no exchange-rate source or date policy in the challenge. `25 lakhs`, Indian comma
notation and `1.2 cr` are normalized deterministically.

Company policy:

- Prefer an explicit organization name with evidence.
- Use `null` if it cannot be supported.
- Do not guess acronym expansions. `NTPC Limited` stays `NTPC Limited` unless the expanded
  name appears in the message.
- Fabricating a company/date/value is worse than returning `null`.

## 10. Replies, idempotency and concurrency

### One task per thread

The required Task API has one assignee and no parent-child task model. The implementation
therefore maintains one current task per thread.

### Reply behavior

- First actionable message: create.
- Actionable reply with changed fields: patch.
- Reply with no material changes: no-op.
- Suppressed new email: skip.
- Field-only reply preserves owner/category unless explicit route or sales-value evidence
  changes them.
- Explicit clear/set/unchanged semantics prevent missing model fields from erasing the
  prior task.
- A corrected deal value can move a thread between Rohit and Aarti.

### Idempotency

The public `POST /tasks` deliberately does not deduplicate because the challenge specifies
that behavior. Idempotency belongs to `/ingest`.

Guarantees used by `/ingest`:

- Unique `(candidate_id, email_id)`.
- Unique `(candidate_id, thread_id, message_index)`.
- Content hash distinguishes an exact replay from conflicting reuse of an email ID.
- Per-thread application lock plus PostgreSQL `FOR UPDATE` serialization.
- Recheck inside the lock closes the race after the optimistic precheck.
- Existing task lookup by thread prevents a second grader-visible task.
- Patch generation compares only mutable fields.
- Event operation keys are unique.

Why a separate delivery table exists:

- The decision for an email is immutable and should not be duplicated on replay.
- The same email may still be delivered in several runs/batches.
- `ingest_deliveries` records each run-specific outcome, including `unchanged`, while chat
  and stats can remain correctly scoped to a selected batch.

Conflict behavior:

- Same email ID + same content → unchanged.
- Same email ID + different content → `409 email_id_content_conflict`.
- Same thread/message index + different email ID → conflict.
- Reply with no stored predecessor/task → `409 orphan_reply`.
- Multiple existing tasks for an ingested thread → conflict instead of guessing which to patch.

## 11. Persistence model

Know the purpose of each table:

| Table | Purpose |
|---|---|
| `tasks` | Grader-visible current task records. |
| `ingest_groups` | Stable frontend client batch identity across chunks. |
| `ingest_runs` | One synchronous request, counters, errors and timing. |
| `ingest_deliveries` | Run/batch-specific delivery outcomes without duplicating decisions. |
| `emails` | Raw/normalized email and immutable identity/content hash. |
| `decisions` | Classification, evidence, reason, model/degraded metadata and task fields. |
| `threads` | One current task mapping/snapshot and update count per thread. |
| `task_events` | Before/patch/after history for creates, updates and no-ops. |
| `quality_feedback` | Human labels: correct, misrouted, missed or spurious. |
| `chat_audit` | Question, validated plan, supporting data, answer and status. |

Why both `tasks` and `decisions`:

- The grader’s Task API contains only current actionable tasks.
- Skipped messages never become tasks but must still be visible to operations and chat.
- Decisions store evidence and reasoning that the Task API does not represent.

Why current snapshots plus events:

- Current-state questions should not reconstruct an entire event log.
- Historical questions such as repeated updates require confirmed events.
- Keeping both makes reads simple and audit history explicit.

## 12. Grounded chat design

Question path:

```text
natural-language question
  → deterministic common-question planner
  → optional Gemini structured planner for unmatched phrasing
  → Pydantic-validated allowlisted ChatPlan
  → scoped repository queries/aggregations
  → supporting_data
  → deterministic grounded answer
  → optional Gemini wording validation
  → persisted chat audit
```

Why no model-generated SQL:

- It expands the security and correctness surface.
- The required question families and broader analytics can be represented as a typed query
  with an allowlisted dataset, fields, operators, aggregate and row limit.
- Unknown questions should fail closed instead of inventing a query.

Why `supporting_data` is returned:

- A grader/user can cross-check every number.
- It distinguishes computed facts from prose.
- It makes zero a first-class result rather than an LLM guess.

How Gemini is constrained in chat:

- Common questions are planned deterministically, so owner/category/priority/confidence
  questions still work without Gemini.
- For unmatched natural-language phrasing, Gemini receives the raw question plus an
  allowlisted analytics schema only. It returns a structured plan, not SQL or facts.
- Pydantic rejects cross-dataset fields, unknown operators, invalid aggregates and limits.
- The deterministic executor alone reads scoped stored data and computes counts, filters,
  group-bys, lists and numeric aggregates.
- During optional wording, Gemini receives only the validated intent, computed data and
  grounded draft, not the raw question.
- Added, removed or changed numeric tokens cause fallback.
- Missing subject terms cause fallback.
- Action and unsupported requests never go through optional wording.

The query layer covers current tasks, decisions, threads, task events, feedback and ingest
runs. It supports counts, lists, compound filters, group counts, null checks, and sum/
average/minimum/maximum over approved numeric fields. The ten problem-statement families
remain explicit deterministic paths, including zero results and action refusal.

Frontend behavior:

- Chat stays locked until the selected batch has completed routing.
- The UI sends the completed client batch ID as scope.
- Suggested questions demonstrate supported analytics without preventing free text.
- Answer details expose the returned supporting data.

## 13. Frontend decisions

Why preview before routing:

- The problem statement explicitly asks for a raw sanity-check view.
- It separates input truth from derived AI decisions.
- Users can catch malformed/wrong batches before causing writes.

Why sequential 100-email chunks:

- The backend contract accepts at most 100 per ingest request.
- A generated 250-email sample becomes `100/100/50` under one client batch ID.
- Sequential submission avoids amplifying Gemini/free-tier pressure and preserves clear
  progress/error behavior.

Why show evidence and confidence:

- The product goal is not “trust the AI.” It is “see it working and inspect why.”
- Human review should focus on triage and low-confidence/high-priority intersections.

Why poll decisions during routing:

- Ingestion is synchronous and may take time on free hosting/Gemini.
- Polling gives the operator visible progress while the ingest response remains the
  authoritative completion signal.

## 14. Reliability and security decisions

- Production refuses to start without Supabase, Gemini, exact CORS origins and the
  expected Supabase project reference.
- Database URLs are validated as PostgreSQL URLs and TLS is required.
- Frontend never receives Gemini or database credentials.
- Candidate ID is normalized and locked to one byte-identical submission identity.
- Request size is capped around 25 MiB.
- Pydantic forbids or validates malformed enums, dates, booleans, collections and ranges.
- Private operational tables are placed in `app_private`, public roles are revoked, and
  row-level security is enabled.
- Normal tests block accidental use of the production database unless explicitly opted in.
- Health means process liveness; readiness verifies dependencies/migrations.

Gemini resilience:

- Low temperature and JSON schema output.
- Small batches and rate limiting.
- Retry with exponential backoff/jitter and `Retry-After` support.
- An incomplete batch is split into individual requests.
- Persistent item failure uses deterministic degradation.
- Degraded mode is stored and confidence is reduced.

Do not overclaim:

- Config values exist for Gemini timeout and concurrency, but verify the deployed SDK call
  actually enforces them before claiming that those controls are active.

## 15. Testing strategy

Explain testing as layers:

1. **Domain unit tests** — routing precedence, exact boundaries, confidence, amounts,
   deadlines, suppression and reply preservation.
2. **Official example tests** — all 12 worked cases from the problem statement.
3. **Adversarial matrix** — prompt injection, forwarded/quoted content, foreign currency,
   threshold ranges, truncation, mixed asks and suppression false positives.
4. **API contract tests** — exact Task API shapes, invalid enums, identity, filters, CORS,
   request size and error codes.
5. **Lifecycle tests** — replay, replies, no-ops, task adoption/conflicts and batch scoping.
6. **Database integration** — hosted atomicity/concurrency with UUID-scoped exact cleanup;
   opt-in to avoid accidental production writes.
7. **Frontend unit tests** — validation, scope reset, chat evidence/errors and feedback.
8. **Playwright workflow** — preview 250 and route sequential `100/100/50` chunks.
9. **Live Gemini tests** — official examples, focused adversarial cases and isolated
   250-message synthetic regression without Supabase writes.
10. **Production HTTP matrix** — public endpoints, invalid inputs, CORS, replay/reply/chat
    and cleanup.

Current evidence to describe carefully:

- All 12 official examples were validated publicly.
- The current README records 162 backend tests passing, with one hosted test opt-in.
- All 14 frontend tests and the production build pass.
- The final 60-message human-reviewed run reported 100% operation and category F1,
  zero missed/spurious tasks, and 97.62% company exact/null match.

Keep the 250-message synthetic regression separate from the final 60-message reviewed
result. Before quoting current test counts, rerun the suite because the repository may
have changed since this guide was written.

## 16. Evaluation honesty

The correct interview answer is:

> I used synthetic and official examples for development coverage, then froze 60
> personally reviewed labels and ran the current Gemini pipeline against them. That final
> run had 100% operation accuracy and category F1, with one company-name exact-match miss.

Why blind labels must be frozen before tuning:

- Looking at model output while labeling contaminates the ground truth.
- Tuning on the evaluation set inflates metrics.
- Per-category precision/recall and a confusion matrix are more informative than a single
  accuracy number, especially because spurious tasks are weighted heavily.

Metrics reported in `EVALS.md`:

- precision, recall and F1 per category;
- skip precision/recall and spurious rate;
- operation accuracy for create/update/skip/no-op;
- exact due date/value/company matches;
- confusion matrix;
- confidence calibration/reliability curve.

## 17. Known limitations and what you would do next

### Multi-owner messages

Current behavior: one triage task containing all asks.

Why shipped:

- The required API supports one assignee and no parent-child relationship.
- Splitting creates unclear reply reconciliation and grader alignment.

Two-week improvement:

- Store internal sub-intents and proposed owners.
- Let a human split/approve them while retaining one canonical external thread task.

### Confidence calibration

Current behavior: deterministic heuristic score.

Why shipped:

- It is explainable before labeled calibration data exists.

Improvement:

- Fit thresholds/calibration using blind labels and reliability curves.

### Company canonicalization

Current behavior: preserve supported explicit name instead of guessing expansions.

Improvement:

- Add an authoritative organization registry or enrichment source with provenance.

### Bounded chat

Current behavior: a generalized but allowlisted analytics grammar over six persisted
datasets, with honest unsupported answers.

Improvement:

- Add deterministic aliases from observed defence questions and evaluate planner accuracy;
  do not jump to arbitrary SQL or expose raw internal database fields.

### Free-tier infrastructure

Current risk: Render cold starts and Supabase pausing.

Improvement:

- Paid always-on service, readiness warmup, latency monitoring and load-tested limits.

## 18. Likely interview questions and model answers

### “Why did you use Gemini at all?”

> Deterministic parsing is strong for exact business rules but brittle for messy language,
> Hinglish, HTML and intent direction. Gemini converts that mess into a typed evidence
> structure. It does not control the final policy or writes.

### “Why not use an agent framework?”

> The workflow is bounded and safety-critical. LangChain, LangGraph, RAG or arbitrary tools
> would add indirection without improving the ten known operations. Plain typed services are
> easier to test and audit.

### “How do you prevent prompt injection?”

> Email text is treated as data inside the extraction prompt. Gemini cannot select arbitrary
> enums or trigger writes directly. Deterministic policy ignores unsupported owner hints, and
> the chat planner can see the raw question but only return a Pydantic-validated read-only
> plan over allowlisted fields. It never receives SQL capability or the database rows.

### “Why is formal RFP always Aarti even below ₹10 lakh?”

> The roster assigns RFP/RFI/tender work to Enterprise Sales. The value split applies to
> inbound direct deals; government/PSU tender is an explicit override. Precedence prevents
> one generic threshold from erasing the more specific rule.

### “Why does sponsorship with ₹4 lakh go to Marketing?”

> The amount’s semantic role is sponsorship package, not deal budget. Intent and amount role
> are separate fields, so money alone cannot turn every email into Sales work.

### “Why is invoice value null?”

> The API field is deal value, not every rupee amount. Invoice and payment amounts are stored
> as evidence but excluded from `deal_value_inr`.

### “Why does uncertainty create one triage task?”

> Dropping one of two material asks is worse than admitting ambiguity. The external API has no
> subtask model, so one low-confidence triage task preserves all asks for human resolution.

### “Is 0.54 a magic model threshold?”

> No. Triage is selected by deterministic ambiguity rules. Its score is then capped at 0.54
> so review queries can reliably identify it. The score is an operational heuristic, not a
> calibrated probability.

### “How do you avoid duplicate tasks?”

> Email and thread-index uniqueness, a content hash, per-thread locking, a second check inside
> the lock and lookup of the existing task by thread. Replays record delivery as unchanged;
> replies patch the existing task.

### “What if two requests process the same thread simultaneously?”

> They serialize on the thread lock/row. After acquiring the lock, the reconciler checks again
> whether the email or task already exists, closing the race between the initial check and write.

### “Why store skipped emails?”

> A skipped newsletter is absent from the Task API, but operations still needs proof that it
> was seen and correctly ignored. Stored decisions also make spam counts and spurious-rate
> questions answerable without re-running Gemini.

### “How can chat guarantee its numbers?”

> The planner emits one allowlisted typed intent. Repository code computes the result and
> returns it as supporting data. The model may translate unfamiliar phrasing into the same
> validated query schema, but it cannot calculate or inject the result. Prose is generated
> from backend-computed data, and optional Gemini wording is rejected if it changes numbers
> or the subject.

### “Why not call Gemini again when chat asks about an email?”

> The system already paid to extract and persist the facts. Recalling Gemini would be slower,
> costlier and potentially inconsistent. Chat queries the stored decision and task state.

### “What does zero mean in chat?”

> It is a computed zero over the selected batch, not a model’s belief. Zero and unsupported are
> explicit valid outputs.

### “Why separate current task state from events?”

> Current queries should be fast and simple, while historical update questions need an audit
> trail. A current thread snapshot plus immutable events supports both.

### “How do you handle Gemini downtime?”

> Batch failure splits to individual requests, retries use backoff, and persistent failures use
> a conservative deterministic extractor. The result is marked degraded and confidence drops;
> the email is never silently discarded.

### “What was the hardest edge case?”

> Direction and context, not keywords: vendor spam containing Marketing terms, replies containing
> quoted old values, and mixed-owner asks. Those drove the separation of extraction, semantic
> roles and deterministic precedence.

### “What would you change with more time?”

> Finish blind human evaluation and calibration first, then add provenance-backed company
> normalization, internal multi-owner sub-intents, active latency/quality monitoring, and expand
> deterministic chat aliases from observed question patterns while retaining the validated
> general planner.

## 19. Things not to say

Avoid these claims:

- “Gemini decides the owner.” It extracts; Python decides.
- “Confidence is the model probability.” It is a deterministic operational score.
- “Every email below 0.54 is moved to triage.” Triage comes first; the cap follows.
- “The 250 synthetic metrics prove production accuracy.” They are development evidence only.
- “The public Task API deduplicates.” It intentionally does not; `/ingest` does.
- “All dates found in an email become deadlines.” Only actionable deadline roles do.
- “All rupee amounts become deal values.” Amount role is decisive.
- “The frontend talks to Supabase/Gemini.” Only the backend does.
- “Gemini generates SQL or computes chat counts.” It only proposes a validated plan and may
  rephrase an already grounded answer.
- “The system can send email through chat.” Chat is read-only and refuses actions.
- “The system never fails.” Explain degraded mode, honest limits and remaining evaluation work.
